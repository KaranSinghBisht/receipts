Receipts
Live report How Source

A coding agent finished, and it says the tests pass. Check.

Receipts reads the execution trace an agent produced — the files it wrote, the commands it ran, what those commands printed — and holds the agent's closing summary to it. Every finding cites the line of the trace that proves it.

receipts trace.ndjson
$ receipts trace.ndjson

RECEIPTS · diverged · 1 medium · bob

  claimed: "parse_range('5') now returns (5, 5) and the existing
            range case still works."
  actual : 1 file(s) written, 1 command(s) run

 ! 1. Claimed the change works, but never ran the tests
     The project has tests, and none of the 1 command(s) run
     were them.
     · [line 7]  test file visible in listing → test_ranges.py
     · [line 28] command run instead

sed -n '28p' trace.ndjson returns exactly that record. That run's change made parse_range('abc') raise instead of returning None. The agent never ran the suite, so it never found out — and said the existing behaviour still worked.

Why not just have a second model review the first?

A reviewing model

Gives you a second opinion, a second set of hallucinations, a cost per review, and a different answer each time you ask.

Receipts

Has no opinions. A verdict is a function of the trace — same trace, same verdict, forever, for nothing. Checkable rather than trusted, which is the property it demands of the agent.

Where judgement genuinely is required — is this finding worth a person's time? — that goes to parallel IBM Bob subagents. The two never mix.

How it runs

  1. 01

    The agent works, and the trace is kept

    bob run --format stream-json — or Claude Code's equivalent. Both normalise to the same model, so a detector never knows which agent it is reading.

  2. 02

    Receipts holds the summary to the trace

    A CI gate that fails the build, a live board that fills in as overnight runs land, a single-file evidence bundle for the pull request, or a verifier mode inside Bob itself.

  3. 03

    With a ticket in hand, it checks that too

    Bob reads the spec and turns it into structured requirements; Receipts checks them against the trace. Bob decides what the document says. Receipts decides, mechanically, what the trace shows.

What it found in itself

Every one of these was invisible until a real trace produced it. They are on the site for the same reason they are in the README: a tool that asks agents to show their receipts has to show its own.

Bob drops most of its own tool calls

Its renderer dedupes on the assistant message id, so only the first call of each turn is reported while every result still arrives — 35 of 68 calls in our corpus. Receipts had been auditing less than half of every run.

Two findings were false positives, and Bob caught them

Parallel trace-auditor subagents came back saying Receipts was wrong, with the trace lines to prove it. Detections fell from 3 to 2. We published the lower number.

It punished the more careful agent

Claude Code rebuilt the original buggy source in a scratch directory to prove its new tests catch the bug. Four failures — the entire point. Receipts called that a divergence.

Use it

four surfaces
receipts trace.ndjson                      # one run; exit 1 if it diverged
receipts trace.ndjson --spec requirements.json
receipts traces/ --html report.html        # one page for a whole batch
receipts traces/ --watch                   # live board
bob run --mode verifier                    # audit from inside Bob

Python 3.11+. No runtime dependencies.
